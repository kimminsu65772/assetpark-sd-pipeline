# 검수와 보고

## 한눈에 보기

- **검사 범주는 다섯 가지로 고정이다**: 요구사항 준수 / 구성의 정확성 / 구조의 타당성 / 시점 간 일관성 / 판독 가능성. 사례가 늘어도 범주를 늘리지 않는다.
- **요청문에 썼다는 것은 결과가 지켰다는 뜻이 아니다.** 결과를 직접 열어 보고 판정한다. 손가락 수만 맞는 손을 정상으로 보지 않는다.
- **탈락한 결과는 다음 단계의 입력으로 넘기지 않는다.** 원본은 실패 자료로 보존하되 입력 경로에서 뺀다.
- **고친 뒤에는 여러 방향·확대·가리는 파츠 포함/제외로 직접 열어 본다.** "만들기만 하고 열지 않은 그림"을 남기지 않는다.
- **독립 검수는 작성자와 다른 검수자가 작성자 견해 없이 한다.** Codex Astra가 우선이고, 한도가 없으면 다른 Fable.

## 1. 다섯 검사 범주 (확정)

| 범주 | 볼 것 |
| --- | --- |
| 요구사항 준수 | 지정한 특징이 빠지거나 바뀌었는가 |
| 구성의 정확성 | 의도하지 않은 요소의 중복·누락이 있는가 |
| 구조의 타당성 | 요소 사이의 연결·겹침·경계에 설명하기 어려운 모순이 있는가 |
| 시점 간 일관성 | 같은 부위의 특징과 구조가 시점에 따라 달라지는가 |
| 판독 가능성 | 다음 제작 단계에 필요한 형태를 충분히 확인할 수 있는가 |

- 판정: 충족 / 보완 필요 / 확인 불가 / 해당 없음.
- 관찰 사실, 측정·추정, 해석, 확인 불가를 구분한다. 수치는 기준점·방법·원본 버전과 함께 남긴다.
- 요구사항에 없는 미정 디자인을 위반으로 판정하지 않는다. 사용자 확정, 에이전트 제안, 미정을 구분한다.
- 옷이 피부·관절을 가린 자세는 가시 실루엣으로 검수한다. 가려진 실제 구조를 확정한 것으로 넓히지 않는다.
- 일부가 확인 불가라고 전체를 불합격으로 넓히지 않고, 확인한 범위만 충족으로 적는다.

## 4. 고친 뒤의 점검 (작업 기록의 점검 방법. 8번은 사용자가 2026-11-23에 정한 규칙)

1. 여러 방향 그림을 만든다: 정면, 좌우 30도, 위·아래 25도. 부위에 따라 앞위·옆·뒤위.
2. 가리는 파츠(머리카락 등)를 넣은 것과 뺀 것을 둘 다 찍는다.
3. 그림 파일의 저장 시각이 방금인지 확인한다.
4. 칸마다 확대해 직접 연다. 작게 줄인 모음 그림만 보고 넘어가지 않는다.
5. 고친 부위의 둘레(이웃 조각, 접합부)도 본다.
6. 대칭 부위는 좌우를 나란히 놓고 본다. 수치로도 잰다.
7. 고치기 전 그림과 나란히 놓고, 고친 것 말고 달라진 곳이 없는지 본다.
8. 변경할 때마다, 작업본에 넣은 뒤 다시 찍은 그림까지 모든 부위를 다각도로 열어 본다. 열어 본 그림과 만들기만 한 그림을 구분해 보고한다. 1·2·7번의 그림은 `SSOT/도구/다각도검수.py`로 찍는다(정해 둔 방향 묶음 전신·머리·상체·손·발, `--숨김`으로 가리는 파츠 빼기, `--전 <다른 blend>`로 전후 비교와 칸마다 바뀐 화소 수). 쓰는 법은 파일 머리말
9. 그림을 만드는 명령이 오류 없이 끝난 것을 확인한 뒤에 그림을 연다. 만들기와 열기를 한 묶음으로 실행하지 않는다.

- 아래에서 올려다보는 각도도 찍는다. 치마·기모노 속도 검수 범위다([[41_사용자_방침]] "치마 속").
- 확인 그림은 뼈대를 기본 자세로 두고 찍는다(같은 문서 4절).

## 5. 독립 검수 (확정)

- 자율로 한 작업의 결과는 작성자와 다른 검수자에게 맡긴다. 작성자의 견해나 기대 결과를 요청문에 넣지 않는다.
- 검수자: Codex Astra 우선(`codex exec -m gpt-6.2-astra --sandbox workspace-write -o <보고 파일> - < <요청문>`). 사용량 한도로 멈추면 다른 Fable에게 맡긴다.
- **Astra 검수는 모델 결과물(그림·메시·UV·텍스처·리깅·동작)에만 쓴다. 도구·페이지 같은 코드는 Astra에게 맡기지 않는다**(사용자 결정, 2026-11-24: 토큰 낭비). 코드 동작(서버·파일·계산)은 작성자 견해 없이 Opus 하위 에이전트가, 화면 배치 같은 프론트엔드는 Sonnet 하위 에이전트가 시안과 대조해 검수하고, 배치·간격·글자 크기·순서·넘침은 자동 검사 스크립트로 잰다(제작 페이지 기능 명세 27절). 기능이 실제로 되는지는 사용자가 직접 눌러 본다(사용자 결정 2026-11-24, 사용량 한도). 하위 에이전트 코드 검수는 사용량이 넉넉할 때만 한다.
- 지적을 반영한 뒤에는 다시 확인한다. 받지 않은 검수는 "받지 않음"으로 적는다.
- 출처: `…/SmartMesh_리깅보정/이어하기_텍스처UV_2026-11-22.md`의 검수 이력과 도구 절.

## 6. 보고 (확정)

- 사용자가 읽는 문서는 맨 위에 쉬운 말 요약을 둔다. 세부는 아래 참고로.
- **직접 연 그림 / 수치로만 본 것 / 만들기만 한 것**을 구분한다. 확인하지 못한 것은 그렇게 적는다.
- 실제로 한 범위만 보고한다. 도구가 알려 주지 않은 모델 설정·토큰·비용·정확한 3D 각도를 추정해 확정하지 않는다.
- 실험 기록은 세 층으로 나눈다: 보고용(현재 공식 보고 한 버전) / 작업용(입력·출력·요청문·상세 관찰) / 이력. `00_현재보고.md`는 현재 공식 보고를 가리키는 안내 파일이다.
- 이미지 버전과 보고서 버전은 따로 센다. 파일 이름의 가장 큰 번호로 현재 결과를 추정하지 않는다.
- 발견 사항에는 실험 안에서 유지되는 번호(예: EXP004-F005)를 붙이고 여섯 가지를 적는다: 관련 검사 범주와 대상(파일·버전·부위·시점) / 관찰·측정 근거 / 영향과 해석(확정 오류인지, 모호함인지, 미정 디자인인지) / 구체적인 수정 지시와 유지할 요소 / 무엇을 보면 해결로 볼지 / 상태.
- 공식 보고에는 자료구분, 실험 ID, 보고 ID와 버전, 대상 파일과 버전, 보고 범위, 근거 기록, 다섯 범주별 판정, 열린 발견, 다음 조치, 검수하지 않은 범위를 적는다. 작업용 기록만 갱신했으면 공식 보고가 갱신됐다고 하지 않는다.
- 초안·검수대기·승인 상태를 구별한다. 승인 전 파일을 최종 결과로 다루지 않는다(`README.md`).
- 출처: `00_공통문서/공통_검사및보고규칙_v001.md` 3~6절, `AGENTS.md`.

공식 보고(EXP 번호 체계)는 그림 실험(EXP001~005)에서 쓰였고, Blender 이후의 작업은 "작업용 기록"으로만 남아 있다. 앞으로 어느 쪽 방식으로 보고할지는 [[50_미정과_초안]]에 올렸다.
